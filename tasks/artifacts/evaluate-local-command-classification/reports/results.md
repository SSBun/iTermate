# 本地运行类型分类实测

## 方法与边界

- 调用现有本机 Laya 服务 `/health` 与 `/v1/decide`，健康接口返回模型 `aac6fef/laya-multilingual-mlx`、ready=true；推理响应 model 字段为 `laya-rl-agent`。未独立验证权重内容。
- 20 个固定样本，每组调用 20 次，共 60 次推理请求；一条基于用户提供的 venom 输出（去掉 Shell 提示与部分排版），其余为人工构造。没有执行样本中的命令。
- 三组：详细四分类、简短四分类、三个独立二元问题。第二、三组在看到首组结果后构造，因此不是独立留出集，不代表生产准确率。
- 预期标签在第一轮请求前设定。所有输入标明命令仍在运行；本次不验证进程存活识别、真实屏幕采集、连续状态转换或生产负载。
- 只请求 127.0.0.1，禁用代理及重定向；令牌仅内存使用、不保存到证据。不更改产品代码、设置、安装目录，不启动或重启 App、Bridge 或模型服务。

## 结果

| 方案 | 标签命中 | 服务端推理中位耗时 | HTTP 往返中位耗时 |
| --- | --- | --- | --- |
| 详细四分类 | 7/20（35%） | 28.375 ms | 30.495 ms |
| 简短四分类 | 10/20（50%） | 29.007 ms | 30.485 ms |
| 独立二元判断 | 不直接等价于四分类，未设组合规则 | 52.364 ms | 未汇总 |

详细四分类推理范围 24.010–164.948 ms；简短四分类为 20.791–131.014 ms。服务已运行，不能把首次请求解释为模型冷启动。

使用所选类别 probability≥0.85 作事后筛选，详细组接受 4/20，其中 3 个正确；简短组接受 8/20，其中 5 个正确。概率不是校准后的正确率，且不等于响应的 confidence 字段。

## 关键错误

- venom 监控阶段：详细组 unknown（所选类别概率 0.3824）；简短组 command（0.8802），均未识别为 monitor。
- 生成文档时引用“Server listening”：两组均误判 service，概率分别为 0.9877、0.9633；高阈值不能避免此误判。
- Vite 已就绪：两组均判 monitor，未按约定识别为 service。
- 安静的 tail：详细组 service；简短组 monitor，但概率仅 0.3543。
- 二元组 venom 的 service、monitor、command 分数分别为 0.9686、0.9737、0.9786；互斥阶段被同时肯定。20 个样本中 9 个有至少两个分数≥0.85，不能直接作为可靠互斥分类器。

## 结论

速度适合轻量本地分析，但这三种提问方式的分类质量不足以直接驱动确定性状态图标；不能承诺简单接入即可解决 venom 场景。可以继续研究输入截取、阶段分离和受约束辅助分类，但需要新样本验证，不能把调参集上的改善当成泛化能力。生命周期仍应来自真实命令事件；模型只能辅助，不应单独判定服务健康或命令结束。

## 补充：venom 上下文对照

保持上述两套四分类问题和选项完全不变，只改变同一 venom 样本的上下文。每种组合请求三次，共新增 18 次调用；每种组合三次返回的类别和概率完全一致。重复请求不是新增独立样本。

| 上下文 | 详细问题：所选类别（monitor 概率） | 简短问题：所选类别（monitor 概率） |
| --- | --- | --- |
| 完整输出，包含命令和运行前提 | unknown（6.82%） | command（4.25%） |
| 命令和运行前提 + 最后一条监控行 | monitor（50.44%） | monitor（93.40%） |
| 仅最后一条监控行 | monitor（99.42%） | monitor（90.03%） |

这说明模型能识别该监控行，完整上下文中的其他阶段信息会影响此样本的分类。不能再把该样本的失败直接解释为模型不理解监控类别。详细问题在保留命令信息时仍仅以小幅优势选中 monitor，表明结果也受问题和输入组织方式影响。

局限：只针对已知样本手动选择关键行，尚未验证自动提取最新阶段；不能普遍只取最后一行，因为它可能只是普通日志、空行或错误堆栈。原评估中的引用误判及其他场景仍未解决。建议下一步验证阶段提取和独立样本，而非直接上线，也不据此否定模型能力。

## 补充：固定窗口自动截取的新样本评估

先保存 16 个样本、预期和截取方法，再调用模型；使用此前的简短四选项，不再调问题。三种方法均保留当前命令和运行前提，只分别保留全部非空行、最后四个非空行、最后一个非空行。共新增 48 次请求，全部成功。

样本为新构造的具体输出，但场景选择受前两轮发现影响；venom 是已知场景的变体，不是全新独立场景。没有从真实终端随机采样，不应把结果称为生产准确率。监控中途重新编译等重叠类别没有作为本轮样本。

| 方法 | 标签命中 | 服务端推理中位耗时 | 所选类别概率≥0.85 时正确/接受数 |
| --- | --- | --- | --- |
| 完整片段 | 8/16（50%） | 24.353 ms | 6/8 |
| 最后四个非空行 | 10/16（62.5%） | 22.228 ms | 7/7 |
| 最后一个非空行 | 8/16（50%） | 18.991 ms | 5/5 |

0.85 沿用此前探索的筛选阈值，仅作描述性统计；最后四行只有 7/16 被接受，不能把 7/7 解读成总体可靠率或零误判保证。

关键观察：

- 最后四行减少构建历史干扰，webpack、Flask 的类别从 command 改为 service。
- Redis 的最后一行“DB saved on disk”丢失服务上下文，判成 monitor；保留四行则判对。
- `tail -F server.log` 中的 HTTP 日志三种窗口均被判 service；即使保留了命令，模型仍把被观察服务误当成观察者本身。
- venom 进入监控后新增五条普通应用日志，监控声明离开末尾四行；完整和最后四行均判 command，最后一行判 unknown。这否定了固定小窗口就足以保持监控阶段的设想。
- 文档引用服务提示仍被判 service；三个信息不足样本均未主动选 unknown。

结论：固定窗口截取有改善，但不足以解决自动阶段识别。可以继续研究“仅在明确阶段变化时更新语义标签、普通后续日志不清除已确认阶段、命令结束时清除”的状态化候选方案，以及区分命令本身与其观察对象。但这些方案尚未实现或实测，不能当成已验证解法。本次只验证了固定窗口基线，未宣称已完成可靠的语义阶段提取。
