# 归档与恢复 Pi 会话

## 使用入口

1. 在 **Settings → Agents** 安装或更新 Pi 集成，并在对应 Pi 中执行 `/reload`。
2. 等待主 Agent 和子代理结束，关闭未完成的 Pi 输入／选择弹窗。
3. 右键点击 Session 行，选择 **Archive Pi Session**，直接执行归档，不再显示确认弹窗。Pi 会先使用该会话当前配置的模型生成摘要（会消耗模型额度），再保存归档、退出并关闭对应分屏。
4. 展开主面板底部的 **Archive** 分区，点击归档行的 **Resume** 恢复；也可以在 **Settings → Archives** 点击 **Resume in iTerm2 / Ghostty**。

面板 Archive 默认折叠，只显示标题；展开后显示归档名称、原工作目录及恢复入口。只有明确点击 **Resume** 按钮才恢复，点击行内名称、目录或空白区域不会恢复。悬停可查看生成的会话摘要、完整 Session ID、终端类型和归档时间；Settings 的归档条目也支持摘要悬停。旧归档没有摘要时显示缺省提示，仍可恢复，不自动调用模型补写。该分区与当前 Session 共用滚动区域，参与顶部菜单的 Expand All / Collapse All；折叠状态只保留在当前面板生命周期中。连接尚未就绪或没有当前 Session 时，Archive 仍可显示。展开只刷新列表，不会自动恢复或删除归档。

归档菜单仅在能明确匹配到一个活跃 Pi 会话、Pi 已空闲、没有排队输入或未发送的编辑器草稿，且没有活跃子代理时可用。运行中、身份不明确、集成未加载、临时 `--no-session` 会话等情况不会关闭终端。不是通过 Session 标题、项目路径或最近修改的文件猜测会话身份。

## 保存内容与隐私

Pi 集成通过 SDK 的 SessionManager 读取当前会话 ID、工作目录、原始文件位置、完整原生条目和当前分支位置，保存：

- 原生 JSONL 会话记录，包含历史分支。
- 一个不进入模型上下文的 `itermate.archive` 自定义锚点，使恢复定位到归档时选中的分支。
- 会话 ID、名称、工作目录、归档时间、原始文件位置、终端类型与 SHA256 清单。
- 当前 Pi 模型生成的中文简短摘要：会话目标、已做工作、结果或未完成事项。

摘要通过当前 Pi 进程的模型接口生成，不启动另一条 Pi CLI、不执行工具、不向原会话追加摘要提示词。输入使用当前分支经压缩与上下文编辑后的可见用户／助手文本及已有分支摘要，不传系统指令、隐藏思考、图片或原始工具输出；长内容保留开头与末尾摘录，因此摘要不是完整历史的替代品。调用使用当前模型及其配置的服务提供方，不能保证模型自动消除所有敏感信息。生成失败、取消、60秒超时、空结果或超长结果时不发布新归档、不退出 Pi，显示错误后可以重试。

原始 Pi 记录不删除。归档是点击时的会话快照，不是整个项目、外部文件、扩展内存状态或子代理工作区的备份；Pi 正常退出的清理钩子仍会执行。

归档位于当前用户 Application Support 的 `iTermate/ArchivedPiSessions` 下，每次独立目录。目录权限 0700、文件权限 0600。会话可能包含提示词、文件内容、工具输出或用户曾输入的凭据；归档不加密，不应上传、提交到 Git 或公开分享。

活跃 Pi 的发现信息位于用户配置目录 `.iTermate/pi-live`，通过私有 Unix socket 与随机凭据联系准确的进程。该目录和 socket 不对其他用户开放；同一用户权限下的恶意程序不在此隔离边界内。应用不会把连接凭据写入归档。

## 安全关闭

归档由目标 Pi 自己生成；摘要生成后重新检查会话身份、当前分支及空闲条件，再写临时目录、校验、持久化并原子发布。只有成功后才请求 Pi 正常退出；应用还会复核归档的 SHA256 和原生会话身份，并要求新归档包含摘要。新操作要求 Pi 已加载支持摘要的新版集成，旧集成需 `/reload` 后才能归档。

随后等待目标 Pi 进程退出，再检查终端是否仍由原父 Shell 占用。iTerm2 使用原生进程信息及可用的 Shell Integration 状态，Ghostty 使用 terminal 的 TTY 与进程信息。身份变化、有新任务占用、Pi 未退出或无法确认安全时，**保留终端**并显示错误；已经保存的归档仍在列表中。

关闭仅针对归档会话对应的分屏，不关闭同一标签页的其他分屏；它是该标签页最后一个分屏时，由终端自然移除空标签页。终端已随 Pi 退出而关闭时，关闭操作视为已经完成。iTerm2 会短暂等待退出后前台进程及提示符刷新，发现另一存活进程则保留分屏；显式关闭不使用 force。若终端由自定义命令、包装器或特殊进程结构启动，可能无法确认原 Shell，此时请检查归档后自行关闭终端。

归档操作限制为 64 MiB 原生 JSONL；超限时不退出 Pi，应使用 Pi 自身的导出功能处理更大的会话。

## 恢复方式

恢复前检查归档文件摘要、Session ID 和工作目录。原工作目录不存在或记录损坏时拒绝恢复，不自动改用其他目录。

应用会在 `iTermate/ResumedPiSessions` 下生成可写副本，在原工作目录的新终端执行以下形式的命令：

```sh
pi --session '<归档中的-session-id>' --session-dir '<本次恢复副本目录>'
```

因此保留用户熟悉的 `pi --session <id>` 方式，同时通过明确的 `--session-dir` 避免命中原始文件或同 ID 的其他副本。ID 不硬编码。若自定义 ID 以 `.jsonl` 结尾（Pi 会将这种参数当成文件路径），改用恢复副本的明确文件路径。路径和参数使用 shell 引号，不向已有会话粘贴命令。

恢复使用 `/bin/zsh -lic` 加载用户的登录交互环境；该环境必须能找到 `pi`。只有新 Pi 集成报告已打开目标副本时才确认恢复。命令缺失、权限不足或集成没有加载时，终端可能已打开，但应用会提示恢复未确认；归档不受影响。检查终端提示后再重试，避免重复打开。

归档快照始终保留，恢复后的新消息写入副本；列表不会自动删除归档。已发现相同 Session ID 的活跃 Pi 时，拒绝重复恢复。

## 验证边界

代码构建、AppleScript 编译和原生 SessionManager 格式兼容检查，不等同于真实用户终端的归档／关闭／恢复验收。更新源码后应由用户自行重新构建运行 App，再重载 Pi 集成。开发期间不应为了验证擅自归档或关闭真实会话。
